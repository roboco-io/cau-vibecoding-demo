# 구단 통합 DB 직무를 증명할 프로젝트 후보

확인일: 2026-10-06. 삼성라이온즈 [목표 공고 분석](samsung-lions-db-role-2026-10-06.md)과 [가상 목표 프로필](../portfolio/profile.md)에 연결한다. Exa로 검색·원문을 조회하고 GitHub API로 코드 라이선스와 파일 목록을 보충 확인했다. 데이터 다운로드·실행과 프로젝트 구현은 아직 수행하지 않았다.

## 추천: 투구 데이터 품질 검사 및 통합 DB API

**문제:** 분석 담당자가 서로 다른 출처의 투구 기록과 선수 정보를 신뢰할 수 있게 조회하려면, 결측·중복·식별자 불일치와 단위를 먼저 처리해야 한다.

**활용 자료:** MLB Statcast 투구 기록 + Chadwick 선수 식별자 데이터. 수집 도구 후보는 MIT 라이선스의 pybaseball이다. Statcast는 공개 조회·CSV 내려받기를 제공하지만, pybaseball의 코드 라이선스를 데이터 라이선스로 간주하지 않는다.

**최소 범위 제안:** 2025년 완료된 MLB 경기 하나와 해당 투수·타자에 필요한 선수 매핑만 사용한다. 날짜를 정하고 자료를 확인한 뒤 실제 데이터 범위를 확정한다. 동일 날짜 전체 데이터나 전 시즌 수집은 첫 구현에서 제외한다.

**처리 흐름:** CSV 원본 보존 → 구조·품질 검사 → 단위·식별자 정규화 → 선수 정보 연결 → DB 적재 → 조건별 조회 API 및 품질 보고서.

| 공고 업무 | 프로젝트 기능 | 완료 여부를 확인할 증거 |
|---|---|---|
| 원자료 누락·오류 검사 | 필수 키·자료형·중복·설정된 범위 검사 | 입력 행별 오류 이유와 원본 위치가 담긴 보고서 |
| 여러 자료의 구조 분석·통합 | 투구의 MLBAM ID를 선수 매핑과 연결, mph를 km/h로 변환 | 데이터 사전·매핑 표·변환 테스트 |
| 통합 DB 저장·관리 | 원본 해시와 수집 시점 기록, 반복 적재 시 중복 방지 | 같은 파일을 두 번 처리해도 투구 행 수가 늘지 않는 테스트 |
| DB 연동 API·앱 유지보수 | 경기·선수 조건으로 조회, 실패·빈 결과 구분 | API 예시와 정상·오류 요청 테스트 |

### 데모에서 보여줄 장면

1. 실제 공개 샘플의 원래 품질 상태를 보고한다.
2. 원본의 별도 복사본에 중복·필수 ID 누락·잘못된 숫자를 의도적으로 추가한다. 이것은 원본 데이터의 결함이 아닌 **시연용 오류 주입**이라고 표시한다.
3. 검사기가 주입한 오류를 정확히 찾고 이유를 설명한다. 정상 데이터와 격리 데이터의 건수도 대조한다.
4. 정상 자료를 DB에 적재하고 같은 입력을 다시 적재한다. 중복이 생기지 않는 것을 확인한다.
5. 경기 또는 투수를 지정해 선수 정보와 투구 기록을 API로 조회한다.

### 정확성 기준

- 타격 속도·각도는 모든 투구에 존재하지 않는다. 상황에 맞는 결측을 오류로 단정하지 않고 필드별 필수 여부를 정한다.
- `(game_pk, at_bat_number, pitch_number)`를 투구 키 후보로 검토하되 샘플의 유일성을 먼저 검사한다. 실패하면 조용히 덮어쓰지 않는다.
- 선수 매핑 실패를 이름만으로 임의 연결하지 않고 미해결 상태로 보고한다. 다른 리그의 ID는 같은 숫자라도 같은 선수라고 가정하지 않는다.
- 원본 수정과 변환을 구분하며, 입력 데이터와 스키마의 버전을 기록한다.
- Statcast 문서는 2026년부터 일부 위치·스트라이크존 지표의 정의 변경을 설명한다. 첫 시연은 2025년 단일 경기로 제한하고 향후 연도 통합 시 측정 정의를 추가 관리한다.
- TrackMan·Hawk-Eye 실장비 연동이나 삼성라이온즈 데이터 운영을 구현했다고 표현하지 않는다. 공개 자료로 관련 처리 역량을 보여주는 프로젝트다.

### 구현 기술 후보

Python + SQLite + FastAPI를 제안한다. Python은 수집·검증 생태계와 연결하기 쉽고, SQLite는 별도 서버 없이 DB 기능을 보여줄 수 있으며, FastAPI는 조회 API를 쉽게 실행·확인할 수 있다. 아직 선택된 기술은 아니다. 첫 구현은 리포트와 API에 집중하고 시각화 화면은 후속 확장으로 둔다.

바이브 코딩 활용 증거는 요구사항과 완료 기준, AI가 제안한 매핑의 검토, 실패한 테스트와 수정, 최종 실행 결과로 남긴다. 코드 생성만을 성과로 삼지 않는다.

## 대안 1: 선수 식별자 통합 레지스트리

Chadwick Register와 Retrosheet 경기·선수 자료를 연결해 이름이 비슷한 선수, 출처별 ID, 연결되지 않은 기록을 관리하는 작은 DB와 API를 만든다. 데이터 결합·참조 무결성·중복 방지에 집중할 수 있고 데이터 사용 안내도 명확하다. 다만 구속·회전·위치 같은 트래킹 데이터 품질을 직접 증명하는 범위는 줄어든다.

## 대안 2: KBO 투구 데이터 품질 점검 도구

Hugging Face의 비공식 KBO Play-by-Play 데이터에서 삼성 경기를 골라 품질 보고서·DB·조회 API를 만든다. 국내 야구라는 맥락은 가장 직접적이다. 속도와 좌표의 단위, 계산으로 도출된 필드, 부분 시즌을 구분해야 한다. 게시자는 CC BY 4.0을 명시하면서 원출처 NAVER Sports의 별도 조건·권리도 안내한다. 추출 저장소는 라이선스 파일을 확인하지 못했으므로 코드를 복사하는 기반으로 채택하지 않는다. 데이터 원출처 조건 확인과 실제 샘플 검증이 선행되어야 한다.

## 다음 선택

추천안은 트래킹 데이터·실제 출처 결합·DB·API를 한 프로젝트에 담으면서 경기 하나로 범위를 줄일 수 있다. 사용자와 후보를 정한 뒤, 데이터 접근과 샘플 구조를 확인하고 구현 범위·완료 기준을 확정한다. 외부 접근 실패를 실제 데이터 성공으로 표현하지 않으며, 가상 대체 샘플을 쓸 때 출처를 구분한다.
