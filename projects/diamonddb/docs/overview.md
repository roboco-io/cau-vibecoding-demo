# DiamondDB Overview

상태: 제안 설계. 작성일: 2026-10-06.

**이번 작업은 설계 문서와 UI 목업까지만 진행합니다.** 아래 첫 버전의 기능과 AC는 향후 구현 목표입니다. 현재 UI는 가상 데이터로 화면과 조작만 검토하며 데이터 처리 완료를 주장하지 않습니다.

추가 사용자 조건: **AWS 서버리스로 운영하고 SQL을 필수로 사용합니다.** 운영 DB는 Aurora DSQL로 확정합니다. 월 10만 요청은 비용 산정의 입력이며 측정된 사용량이 아닙니다. [서버리스 아키텍처](architecture.md)와 [비용 산정](cost-estimate.md)을 참조합니다.

## 왜 만드는가

구단의 분석 담당자는 경기·선수별 투구 데이터를 조회하고 싶지만, DB 담당자는 그 전에 입력의 누락·중복·단위·선수 식별자 문제를 확인해야 합니다. DiamondDB는 **품질을 설명할 수 있는 데이터를 일관된 DB에 저장하고 조회하는 과정**을 보여줍니다.

삼성라이온즈 공고의 원자료 품질 관리, 통합 DB 저장·관리, DB 연결 시스템 유지·개선 업무에 대응합니다. 이는 공개 자료로 업무 역량을 증명하는 학생 프로젝트이며 구단 내부 시스템을 재현하거나 운영 경력을 주장하는 프로젝트가 아닙니다.

## 누구를 위한 것인가

| 사용자 | 해결할 일 | 확인할 결과 |
|---|---|---|
| DB 담당자 | 입력 구조와 오류를 확인하고 안전하게 적재 | 실행별 품질 보고서, 격리 이유, 재적재 결과 |
| 분석 담당자 | 경기·선수 조건으로 투구 기록 조회 | 선수 정보, 구속, 데이터 누락 표시 |

## 첫 버전의 범위

- 사용자 선택: MLB Statcast 투구 데이터 + Chadwick 선수 정보, DB 담당자와 분석 담당자 모두를 위한 처리·조회 화면.
- 설계 제안: 2025년 완료된 MLB 경기 한 개. 실제 경기 ID는 다운로드 접근성과 키 유일성 확인 후 데이터 manifest에 고정합니다. 문서 단계에서는 임의의 경기 번호를 만들지 않습니다.
- 투구 데이터와 선수 매핑을 로컬 파일로 보존하고 출처·버전·해시를 기록합니다.
- 필수 키·자료형·중복·단위를 검사하고, 유효 자료와 격리 자료를 구분합니다.
- 선수 정보를 연결하여 DB에 저장하고 같은 자료의 재적재가 투구 수를 늘리지 않게 합니다.
- 조회 API와 간단한 화면에서 경기·투수·타자를 선택하고 투구 목록·품질 기록을 확인합니다.
- 라이브 중 네트워크에 의존하지 않도록 사전 확보한 입력을 사용합니다. 확보 실패 시 가상 샘플이라는 표시를 유지합니다.

## 완료 기준

| ID | 기준 | 남길 증거 |
|---|---|---|
| AC-01 | 출처·조회 조건·해시·스키마·규칙 버전으로 입력을 추적 | manifest와 실행 기록 |
| AC-02 | 알려진 오류 주입을 탐지하고 정상적인 선택 필드 결측을 허용 | 기대값과 실제값 비교 테스트 |
| AC-03 | 잘못된 행은 이유와 함께 격리되고 정상 행만 적재 | 행별 품질 보고서와 건수 대조 |
| AC-04 | 실제 두 자료를 선수 ID로 연결하고 실패는 명시 | 조인 검증 및 미해결 경고 |
| AC-05 | 같은 입력을 두 번 처리해도 투구 수·값이 변하지 않음 | 재적재 전후 DB 비교 |
| AC-06 | 동일 키의 변경된 값은 자동 덮어쓰지 않음 | 충돌 격리 테스트 |
| AC-07 | API와 화면의 필터·빈 상태·오류 표시가 일치 | API 테스트 및 브라우저 확인 |
| AC-08 | 원본과 오류 주입본, 목표와 실행 결과를 구분 | 보고서·README·포트폴리오 기록 |

완료 기준은 아직 달성하지 않았습니다. 처리 속도·정확도·채용 성과 수치는 실행 전 제시하지 않습니다.

## 첫 버전 이후

여러 경기·연도 통합, 구단·공급 업체별 어댑터, 수정 데이터 승인 반영, 장시간 워크플로우는 후속 후보입니다. AWS 배포·사용자 인증은 운영 설계에 포함하지만 이번 작업에서 구현하지 않습니다. 첫 버전에서는 승부 예측·모델 학습·실시간 수집을 넣지 않습니다.

## 포트폴리오에서 설명할 내용

문제 → 입력의 한계 → 품질 정책 → 통합 구조 → 조회 결과 → 검증 근거의 순서로 보여줍니다. AI가 만든 초안을 어떤 기준으로 수정했는지 설명하고, 실제로 성공한 테스트와 남은 한계를 분리합니다.
